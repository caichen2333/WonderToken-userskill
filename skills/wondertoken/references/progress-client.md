# One-pass progress workflow

新版优先规则：realistic-v2 仅用于新出发旅行，默认不重游城市或景点，按独立活动和过夜安排自然归家。下面的固定10/28日和450–500字要求仅适用于旧版；新版以保存的 executionPlan 和 submissionRequirements 为准。新来信可以通过 activityRefs 选择已发生的活动，完整长窗口由同一run内部拆批处理。离线没有缓存正式计划时返回 OFFLINE_CONFIRMED_PLAN_REQUIRED，不改走旧版规划。

This file documents the legacy compatibility workflow only. For every normal v3 progress query use `progress-run.mjs` from [progress-run.md](progress-run.md). Enter this workflow only after `progress-run` explicitly reports an unsupported v3 protocol; permission, network, validation and business errors do not authorize a fallback. The legacy script creates operation IDs, copies the prepared query handle into later requests, runs local preflight, saves complete recovery responses and prints the next decision fields.

Create a private temporary directory and write `source.json`, `facts.json` and `letter.json` with a real JSON serializer or file tool. Do not use `echo`, shell interpolation, or handwritten escaped JSON. Source contains `kind: "user-progress"`, the exact user request in `text`, and an optional real `messageRef`. Authorized scheduled requests use `kind: "authorized-automation"` with the original user authorization and its reference, never an invented approval. Explicit read-only/pause restrictions route to state without preparation or offline replay. Business files contain only agent-authored fields: facts contain movements, activities, optional local news, expenses, totals, return estimate and `finalize`; letter contains content, continuity, image brief and optional recalled Soul IDs. No credentials, operation ID, query ID or revision belongs in them.

```text
node "<absolute-skill-root>/scripts/progress-workflow.mjs" query --source "<temp>/source.json" --output "<temp>/prepared.json"
node "<absolute-skill-root>/scripts/progress-workflow.mjs" lock --input "<temp>/facts.json" --context "<temp>/prepared.json" --output "<temp>/locked.json"
node "<absolute-skill-root>/scripts/progress-workflow.mjs" submit --input "<temp>/letter.json" --context "<temp>/locked.json" --output "<temp>/submitted.json"
```

The call performs local preflight before opening a network connection. It reports all detected errors with array indexes and valid stay intervals, and marks `sent: false`. Fix all errors together; retain valid food/lodging expenses, placing them between arrival and the next departure. Transport expenses may use either allowed endpoint; changing endpoints does not fix a stay-time error. This preflight checks common invariants, not every server rule. Server validation remains authoritative.

After a successful lock, use its `submissionRequirements` to compose the letter and image brief. These requirements already select the permitted focal landmarks, necessary character names, and scene type for the journey's actual encounters. Do not infer that a homecoming letter needs a `homecoming` image moment. Write one 450–500-character body in 3–4 paragraphs, targeting 470–490 characters including paragraph separators.

For recovery, a prepare response with `phase: locked` itself serves as the submission context. Never relock those facts. The workflow writes each exact request beside its output as `<output>.request.json`; reuse that request only for an uncertain retry with unchanged semantics. A normal workflow call already validates, so a separate validation call is unnecessary.

A completed `submit` persists the letter, settlement and durable completion state, immediately prints their compact result, then starts Soul preparation and server-side `generate_memory_image` concurrently in the same invocation. Keep the host execution session alive until the command completes; a tool yield is not the end of the workflow. Give short progress updates while waiting. Do not send the final homecoming reply or defer work to an archive read, heartbeat or scheduled task during normal completion.

The command returns a `completionContext` path and isolated `.soul.json` and `.image.json` result paths. Read the Soul file once, follow [soul.md](soul.md) to author and submit the evolution, and pass the saved submission result to `completion-finish --context <completionContext> --output <completionContext> --soul-result <result.json>`. Read the image result once. The workflow retrieves native image content through `get_memory_image`; the client saves these tool attachments privately and returns `attachments[].path`. Embed that absolute path directly as `![旅行纪念照](/absolute/path.png)` in the final letter. Never open a website preview for this attachment. If `deliveryError` is present, retry only the read-only `get_memory_image` with the journey ID; it can also deliver an existing archived image without regeneration. Prefer native image content or an existing local image file returned by the tool, embedded with an absolute filesystem path. A JSON result file is not an image. Otherwise embed the saved media URL only when the host permits it; a localhost URL does not guarantee inline rendering. A browser/site preview is not an inline image and must not be presented as successful inline delivery. If the host cannot display the image directly, clearly distinguish successful generation/archive from unavailable inline display and provide a labeled image link as the fallback. Do not download remote media to bypass host display restrictions or regenerate an archived image just to obtain an attachment. Image generation already uses the archived pet visual; do not load local Codex Pet files or upload the image again.

Run `completion-status --context <completionContext> --output <status.json>` before final delivery. Return the saved letter verbatim, settlement, home state, growth, Soul changes and image together. A real image or Soul failure does not roll back settlement: report the actual failure and preserve the context for recovery. Do not imply that a pending job is running in the background.

For interruption or uncertain network recovery, run `completion-prepare --context <completionContext> --output <completionContext>` once. It reuses the image operation ID, runs only pending jobs and retains successful results; replaying the completed submission also preserves completion state. Do not regenerate a saved image. Once the host has submitted Soul, use `completion-finish` with its result. If image generation actually failed, use `completion-finish --image-outcome <actual reason>` to record it. Do not use an image failure outcome just because a result is slow, the host yielded, or the first image is aesthetically imperfect. Only a wrong pet/required companion, malformed anatomy, or wrong panel count/aspect ratio permits a single correction.

## Session and host permissions

`session.version=progress-session-v1` and `session.next` identify the persisted stage. Continue `lock → submit → complete-homecoming` in this interaction; `next=deliver` or `status=home` delivers the saved result without starting another trip. At day 28, `session.outcome=homecoming` is compulsory. Source evidence persists with the query; it is not an independent host permission grant. Existing prepared/locked responses remain recoverable; do not recreate already locked facts.

Use normal sandbox permissions first. Existing identity reads, optional schema caching, and an empty offline queue do not require writable global state. Do not unconditionally escalate every stage. If the host requires escalation, first run the local read-only command `progress-workflow.mjs review --context <current-context>` and use its source, journey, stage and exact effects in the formal permission request. Explicitly connect it to the user's request; lock freezes facts but does not charge coins or complete the journey, submit charges only virtual coins. Never describe the phase as a new request to approve a route or bill. Review output is evidence for host inspection, not permission to bypass a denial.

On a denial, preserve the request/context and report the actual host boundary. Do not change the command to bypass review, disable protections, or claim a Skill/authorization field overrides host policy. Use a real user authorization or independently checked effects as evidence where the host permits reconsideration. No second business confirmation is part of the game flow.

Run `setup.mjs doctor` when upgrading or diagnosing: `installation` gives the actual loaded path and release hash, and `progressProtocol` identifies server support. An old server rejecting `requestSource` needs a service upgrade; do not silently strip the source or fall back to a stale plugin copy.
